# 轨迹偏离点检测：论文依据与实验算法

当前检测器是实验算法，支持离线全量分析和 API 录入后的局部检测。目标是识别位置采集错误，保留原始坐标与 ID，并输出可解释的候选标记。本文仅描述算法、接口和可复现命令；个人轨迹、设备信息、复核结果和部署记录保存在被 Git 忽略的 `.local/`。

## 论文与方法选择

| 论文 | 方法与启发 | 本项目的使用方式 |
| --- | --- | --- |
| Yu Zheng, [Trajectory Data Mining: An Overview](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/TrajectoryDataMining-tist-yuzheng_published.pdf), ACM TIST, 2015，§3.1 | 比较均值／中值、Kalman／粒子滤波、速度与距离启发式；指出连续错点和稀疏采样时简单平滑的局限 | 以时间、速度、空间偏离联合检测；单条超速边不直接归因于某一个点 |
| Song et al., [SCREEN: Stream Data Cleaning under Speed Constraints](https://sxsong.github.io/doc/15sigmod-screen.pdf), SIGMOD, 2015 | 用速度约束和窗口清理时序数据，尽量保留原始信息；主要处理单变量 | 借鉴约束思路，速度使用球面距离计算，联合处理经纬度 |
| Chen et al., [Trend-Residual Dual Modeling for Detection of Outliers in Low-Cost GPS Trajectories](https://pmc.ncbi.nlm.nih.gov/articles/PMC5191017/), Sensors, 2016 | TRDM：三次平滑样条提取趋势，再用 ARMA 与异常残差评分寻找偏离 | 作为后续小幅漂移检测的对照；当前未实现 TRDM，也不把简单插值冒称为 TRDM |
| Zhang et al., [Multivariate Time Series Cleaning under Speed Constraints](https://arxiv.org/abs/2411.01214), PACMMOD 2(6), 2024，§2.2.2 | MTCSC-G 用动态规划找速度相容的最长子序列，以最少修复点为目标；另有在线、聚类与自适应版本 | 第一版核心借鉴 MTCSC-G，改成短窗口、固定两端、球面距离、候选标记；没有复现完整 MTCSC-C/A |
| Duarte & Sakr, [Outlier Detection and Cleaning in Trajectories: A Benchmark of Existing Tools](https://ceur-ws.org/Vol-3379/BMDA_2023_paper_1870.pdf), BMDA, 2023 | 区分整条轨迹异常与轨迹内错点，并用额外传感器建立真值 | 实际记录没有真值标签，候选数量不能当作准确率；后续需人工标注与对照实验 |

以下选择是针对本项目数据条件的工程判断：首版采用速度约束与最少标记点，适合明显跳点和短时连续错误定位。TRDM 可在后续补充小幅漂移识别；采用前必须检查不规则采样、转弯与停留对拟合的影响。Kalman 更适合有运动模型和测量误差信息的估计任务，目前原始表没有 accuracy、定位来源、速度或航向。纯空间聚类无法仅凭位置疏密区分旅行中的陌生地点与采集错误，因此不作为第一版唯一判据。

## 短窗口：带两端约束的最长相容子序列

实现位于 `worker/api/src/trajectory.ts`，当前版本 `excursion-v3-experimental`。短窗口保留 v1 的 30 分钟约束。

1. 按设备分组，按观测时间和 ID 排序。同设备同时间同坐标仅在分析视图去重；同时间不同坐标记录为冲突，并切断推断。原始记录不变。
2. 找短时间窗口两端 A、C，中间最多 8 个观测点。超过 30 分钟的采样间隔或整个窗口不参与偏离段归因。
3. 检查进入／离开中间段的速度是否异常、A 到 C 的速度是否合理，以及两端外侧观测是否支持这两个锚点。窗口外仍有跳变时尝试更宽的窗口，避免用错点当锚点。
4. 在窗口内建立按时间向前的图。点 i 到 j 的边仅在 `0 < Δt ≤ maxGapSeconds` 且 `greatCircleDistance(i,j) / Δt × 3.6 ≤ S` 时存在。固定 A、C，在图中动态规划寻找保留点数最多的路径；同样多时选择距离更短的路径。
5. 不在这条路径上的点才成为候选。它们还必须偏离最近两侧保留点的时间插值位置至少 1 km，且原路径相对 A→C 的绕行比至少为 4。插值用于证据评估，不写回坐标。
6. 两端进出速度均超过 500 km/h、且两侧都有近邻支持时标为 `high`；其他通过检查的段标为 `review`。这些名称是规则强度分级，不是校准后的概率。
7. 候选窗口按证据强度择优，保护保留点与锚点，最多进行 3 次高置信候选的虚拟移除。随后输出其他候选和未归因的极端跳变；虚拟移除只用于本次计算。

局部速度上界为：

```text
S = max(minSpeedKmh, 3 × A→C速度 + 30, 3 × 外侧近邻平均速度 + 30)
```

这里的倍数、30 km/h 裕量、1 km、绕行比和窗口上限是工程起始值，不是论文为本数据验证过的常数。邻近速度超过 `max(350, 3 × A→C速度 + 30)` 时锚点不受信任。后续应使用标注数据校准。

一条超过 1500 km/h 的边，如果没有被短窗口或长间隔往返候选段解释，进入 `unresolvedJumps`。它表示两个端点之间不合理，不能独立确定是哪个点错了。超过 30 分钟的间隔另外输出 `gaps`，保留采样缺口证据，即使其中的偏离已通过往返规则归因。

单个候选窗口最多 W+2 点，动态规划 O(W²)；枚举不同长度窗口约 O(nW³)，W 默认固定为 8。整个设备序列先排序 O(n log n)。API 通过有限窗口控制每次请求的计算量，未用离线全量的本机耗时作为 Workers 性能保证。

## 长间隔往返归因

v2 为超过短窗口条件的候选增加独立检查，默认 `maxReturnSpanSeconds = 10800`（3 小时）、`maxReturnDistanceMeters = 1000`（1 km）。这两个值也是工程起始值，尚未通过人工真值校准。

1. 同设备的窗口仍最多包含 8 个中间观测点，并保持时间冲突切断与重复记录处理。两端 A、C 的间隔不超过 3 小时，且相距不超过 1 km，构成返回原处的证据。
2. 进入与离开候选段的速度均须超过局部速度上界 S，且至少一侧超过 1500 km/h 的极端速度门槛。普通飞机速度的往返不会仅因飞得快而进入这条规则。
3. 检查两端外侧相邻观测。间隔不超过 3 小时、距离不超过 1 km，且速度未超过原有锚点可信上界的观测，才能为长间隔锚点提供支持。长时间平均速度低，但外侧位置很远，不能算稳定支持。
4. 至少一侧有支持才输出候选；两侧都有支持、进出速度均超过 `max(500, S)` 时为高置信，否则为待复核。缺少所有外侧支持时仍保留为未归因跳变。
5. 在这个有限窗口内继续使用最长相容子序列，保留物理上合理的内部点。候选仍需偏离至少 1 km、绕行比至少为 4；超过 3 小时的间隔不通过这条规则。

证据原因分别为 `long_return_spike` 和 `long_excursion_burst`，保留两端锚点、内部保留点、进出速度、旁路速度、偏离距离和外侧支持数量。判定依赖候选段两侧证据，不把单条超速边直接归因于某一个端点。

这条规则与短窗口共用候选排序、锚点保护及虚拟移除过程，不增加 API 的读写窗口大小，也不删除或替换原始坐标。

## 历史位置匹配

v3 在几何判断全部结束后，仅为已识别的候选查找历史参考，保留 v2 的候选选择、往返归因和等级。参考必须是同一已知设备、观测时间至少早 24 小时、球面距离不超过 100 米的记录。24 小时和 100 米是初始工程参数，用来分离当前偏离段与较早的访问；较近时间的定位重用目前不会得到这个标记。没有命中也不能作为位置正确的证据。

离线排除全部已知候选、未归因跳变端点、时间冲突、无效点及其重复记录。实时参考必须已标为 `retained`，或在当前窗口被重新判断为保留，并排除当前窗口已发现的异常。当前重算与候选证据在设备版本校验后一起提交，避免使用本次已经判断不可靠的参考。`retained` 是算法状态，不是人工确认。

`historicalMatches` 保存当前点 ID、旧点 ID、旧点观测时间、球面距离、间隔秒数和 `searchComplete`。多个旧点同样近时优先使用时间较新的记录。离线完整遍历可用历史；实时通过新增 `(Device, Latitude, Longitude, Date, ID)` 索引查询球面范围的包围盒，再计算真实距离。日期变更线范围拆分查询，极区覆盖全部经度。

实时每个需要更新的候选最多返回 64 条原始空间候选和 1 条截断哨兵，再关联其质量标记；保留状态筛选和异常参考排除在 Worker 中完成，避免为凑够可信参考而扫描、关联大量错误定位。候选密集时 `searchComplete=false`，匹配仅表示在返回子集中找到了旧点，不保证是全库最近的旧点，也不保证找出了所有匹配。索引减少位置范围的扫描，但数据库实际扫描量仍取决于该区域的记录密度；查询截断是结果上限，不是数据库扫描行数上限。历史查询失败时保留主检测标记，并记录历史查询不可用。

每次分析尝试最多执行 2 个历史位置查询，优先处理最接近当前录入点的候选。顺序上报时，同一候选段可复用已完成的历史证据，前后锚点、候选 ID 或内部保留点变化时重新查询；待复核升级为高置信但段落不变时，可以沿用匹配。历史补报会刷新重算范围内的候选，当前窗口发现参考已经不可靠时也会使缓存失效。截断、查询失败和超预算的证据不会作为完整结果缓存。

完整证据复用不额外查询窗口外的参考，不能保证立即察觉远处旧记录的质量变化；负结果也可能在范围外的补报后滞后。这与局部重算的限制一起保留，历史证据不参与异常等级，人工全量重算仍可统一结果。超出本次查询数量的候选记录 `historicalSearch.reason=candidate_limit`，主检测标记仍正常保存；没有独立的历史查询补算队列。查询预算见下文。

“接近旧位置”可能与旧定位被重新上报有关，也可能是正常重访。现有表没有定位源、accuracy 或定位生成时间，不能据此确认缓存错误。这个信号保留在 API 证据中，不单独生成异常、不自动提升等级。Console 以轨迹浏览为主，默认隐藏 `outlier`、`review`、`uncertain`，不展示质量列、算法提示和匹配详情；筛选菜单可以临时显示原始点。

## 每次录入的局部检测

`worker/api/src/location-quality.ts` 将同一个检测器接到新旧上报接口。请求流程为：

1. 用 [D1 batch 事务](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) 同时推进设备分析版本、保存原始位置与初始 `pending` 标记。
2. 用一条 SQL 合并两个 `(Device, Date, ID)` 索引范围、设备版本和已有标记，提供同一读取快照。前后各至多 64 个点，加上新录入点，实际分析不超过 129 个点；另有每侧一个截断哨兵，不参与几何分析。也适用于乱序补报。
3. 用整个窗口提供上下文，重算新点前后各最多 27 个邻点的标记；时间重复组完整传播标记。只把状态、原因、算法版本或证据发生变化的标记写回，超出范围的旧记录保持原来的标记或 `unassessed`。
   随后为这些标记中的偏离候选执行有限的历史位置查询，添加辅助证据，不增加几何分析窗口。
4. 数据库写入质量标记时原子校验设备版本；没有变化需要写回时，也要查询版本确认快照没有过时。如果窗口读取之后又有同设备新上报，重新读取最新窗口，最多尝试两次。通过 [D1 JSON 查询](https://developers.cloudflare.com/d1/sql-api/query-json/) 一次写入变化的标记。
5. 成功时直接返回已通过版本校验的快照标记，省掉一次重复读取；只在检测延后时回读数据库标记。无需队列、定时任务或全库扫描。

`analysis.updatedPoints` 是本次分析实际写回的标记数，不包含录入事务创建的初始 `pending`。`state=updated` 且 `updatedPoints=0` 表示窗口已完成检查、没有标记变化。未变化的标记不刷新 `checkedAt` 和行版本，`checkedAt` 表示最近一次保存该标记的服务端检查时间。成功响应反映通过版本校验时的结果，之后到达的新观测仍可能改变它。

## D1 请求与读写预算

每次录入保留同样的几何检测规则，在 Worker 内计算，D1 只负责有限窗口读取与变化结果持久化。初始入库仍是三条 SQL 的原子 batch，不牺牲原始位置、设备版本与初始标记的一致性。

| 情况 | 之前每次录入的 SQL 数 | 当前 SQL 数 |
| --- | ---: | ---: |
| 不需要新增历史查询，无重试 | 8 | 5 |
| 历史查询达到预算，无重试 | 24 | 最多 7 |
| 两次分析尝试都达到预算 | 44 | 最多 11 |
| 两次尝试未完成，回读当前标记 | 44 | 最多 12 |

常规请求是入库三条、窗口快照一条、变化写回或无变化版本校验一条，总计五条 SQL、三次 D1 调用。稳定轨迹只需把一个旧 `pending` 改为 `retained`，避免每次重写前 27 个旧点和新点。重复检查相同且未发生并发变化的窗口时只读、不写。首次分析未标注的历史、候选等级改变、冲突和补报仍可能一次写回多个标记，这是修正旧结果所必需。

SQL 数低于 [D1 Free 每次 Worker 调用 50 个查询的限制](https://developers.cloudflare.com/d1/platform/limits/)。[D1 计费与每日额度](https://developers.cloudflare.com/d1/platform/pricing/) 主要依据实际扫描和写入行数；batch 减少数据库往返，但其中每条语句及写入的每行仍计量，索引维护也会增加写入量。返回 131 个窗口记录或 65 个历史候选不等于只计费这些行。

测试在已有 70 点和 3,000 点的稳定设备轨迹中，验证每次五条 SQL、三次调用、一条旧质量标记变化；本地 D1 返回的计量在这两组样例中均不超过 500 行读取和 10 行写入。这是样例回归预算，不是所有生产数据的硬扫描上限，线上仍应通过查询 `meta.rows_read`／`meta.rows_written` 和 D1 Row Metrics 观察实际消耗。历史位置扫描尤其受该坐标附近的密度影响。

`pending` 表示还没有足够的后续观测。新点附近一条明显不合理的边可以立即标为 `uncertain`，但不能据此确定新点错误；返回路径出现时可能升级为 `review`，再有外侧支持点时才可能达到 `outlier`。持续高速行程不会仅因速度高而被标记。所有标记允许后续更新，最初的正确判断也不是永久锁定。

`GET /api/location` 和 `GET /api/locations` 默认 `view=raw`；`view=filtered` 仅排除 `outlier`，其他状态均保留。过滤在分页之前进行。质量证据包含算法版本、原因、锚点、保留点、速度、偏离距离及候选的历史位置匹配；原始坐标不替换、不删除。旧查询仍返回原始记录。

录入已提交后，标注故障或并发变化超出两次尝试上限会返回 `analysis.state=deferred`，同时保留成功入库的原始位置和初始标记。后续邻近观测可触发重算；当前没有独立的重试队列，也不保证长时间没有邻近上报的失败窗口会自动补算。

局部窗口的结果可能与离线全量结果不同，特别是在边界、长错误定位簇和缺少后续观测时。当前 `outlier` 仍指规则支持较强的候选，过滤视图应与 raw 视图一起用于复核。

## 如何验证

单元测试用合成坐标检查：孤立跳点、连续错点夹着正常点、偏离直线但速度合理的正常点、连续高速移动、正常往返、小幅抖动、设备隔离、长间隔、时间冲突、重复记录、无效坐标及跨日期变更线。

离线脚本对全量记录输出候选与逐段指标，并比较不同速度下限。数量稳定只能说明参数敏感性较小，不能证明识别正确，也不意味着已找出全部错点。

下一步评估应在独立轨迹段建立标注：明显跨城跳点、连续错点、路口转弯、停留、驾车／高铁／航班、长间隔转场和较小漂移。按时间段划分调参与验证集合，分别测量 precision、recall、正常点误标率，重点看整段错误定位中的正常点是否被保留。

当前已知限制：没有返回证据的长间隔转场、超过 3 小时的长往返、轨迹开始／结束的单侧错点、超过窗口长度的错点簇、速度仍合理的错误定位、1 km 内漂移可能漏检。速度相容只代表物理上可能，不代表位置真实；真实曲折路径也可能触发候选规则。

## 可复现的本地分析

Wrangler 仅调用项目依赖，分析数据放在 Git 忽略的 `.local/` 下。以下命令读取远程数据库，不应用迁移或修改数据：

```bash
mkdir -p .local/trajectory-analysis/new-snapshot
chmod 700 .local .local/trajectory-analysis .local/trajectory-analysis/new-snapshot
pnpm --dir worker run wrangler d1 export DB --remote \
  --output ../.local/trajectory-analysis/new-snapshot/snapshot.sql \
  --skip-confirmation
chmod 600 .local/trajectory-analysis/new-snapshot/snapshot.sql
python3 scripts/trajectory/prepare.py \
  .local/trajectory-analysis/new-snapshot/snapshot.sql \
  .local/trajectory-analysis/new-snapshot
pnpm --dir worker run analyze:trajectory \
  ../.local/trajectory-analysis/new-snapshot/locations.json \
  ../.local/trajectory-analysis/new-snapshot
```

`prepare.py` 将完整 SQL 导入本地 SQLite，校验完整性，导出全部 Locations 与 Projects；不会覆盖已有 SQLite 文件。JSON 保留旧表字段和原始记录。分析脚本也接受 `/api/locations` 的字段格式，但输入应是完整轨迹集合，而不是孤立的一页。

分析输出：

- `analysis.json`：完整检测结果，包含原始 ID、保留点、锚点、速度、偏离距离、原因与参数。
- `summary.json`：设备统计、采样／速度分位数、基线数量、速度下限敏感性和输入哈希。
- `findings.csv`：逐点候选，可定位回原始记录；段级指标会在同段各候选行重复。
- `unresolved.csv`：仍不能归因到点的极端跳变边。

可选图表报告需要项目本地的 Python 环境：

```bash
python3 -m venv .local/trajectory-analysis/venv
.local/trajectory-analysis/venv/bin/pip install matplotlib
.local/trajectory-analysis/venv/bin/python scripts/trajectory/report.py \
  .local/trajectory-analysis/new-snapshot
```

`report.html`、图表和原始数据均留在本地。离线脚本不会将结果写回远程数据库或 API 质量表。API 已保存算法版本与独立质量标记，查询支持 raw／filtered 视图，并为后续观测到达后重新判断保留空间。
